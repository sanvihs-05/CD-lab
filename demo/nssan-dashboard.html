NSSan catches the numbers going wrong.

A compiler sanitizer that re-runs every float operation in double precision, compares the two, and reports — with file, line and column — exactly where precision silently collapses. Turn it on like any sanitizer: clang -fsanitize=numerical.

$ ./buggy_san  —  1.0f - cosf(0.0001f)

What just happened

1.0f − cosf(0.0001f) should be ≈ 5×10⁻⁹. But in float the cosine rounds to exactly 1.0, so the subtraction annihilates every digit — the program returns 0 and exits without complaint.

The three-step demo

The same bug, told three ways — silent without the tool, caught with it, and a clean baseline that proves NSSan doesn't cry wolf.

01 · without NSSan clang -g buggy.c Result: 0 — a plausible-looking, totally wrong answer. Nothing warns you. SILENT BUG
02 · with NSSan clang -g -fsanitize=numerical buggy.c Catastrophic cancellation pinpointed at buggy.c:6:23 with the float/shadow divergence. CAUGHT
03 · clean baseline clang -g -fsanitize=numerical clean.c Result: 0.75 — 0.25f + 0.5f is exact, so NSSan reports CLEAN. NO FALSE POSITIVE

How it works

An LLVM IR pass shadows each covered float operation; a small runtime library compares the results and reports divergence beyond a configurable threshold (default 1e-5).

STEP 1

Source → IR

Clang lowers your .c to LLVM IR. -fsanitize=numerical auto-loads the pass and links the runtime.

STEP 2

Build shadow

For each float value the pass keeps a double shadow in a DenseMap<Value*,Value*>.

STEP 3

Replay in double

The operation runs again in double — the ~16-digit answer the ~7-digit float ought to have produced.

STEP 4

Compare & report

The runtime checks relative error, classifies the issue, dedupes by site, and prints a verdict at exit.
